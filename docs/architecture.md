# Architecture

## Three levels

- **Session** — a Claude Code session running as the project's entry role (`task-manager`, or a project's own). It starts loops and carries the owner's answers into them. It never calls a role and never decides for the owner.
- **Loop** — a natural-language definition (`.claude/loops/<loop>.md`, the authority) and the workflow script generated from it (`.claude/workflows/<loop>.js`, stamped with the definition's digest). A script only calls roles, orders and branches on their structured output, passes inputs between them, loops within a bound, runs another loop as one step (one level deep), and stops for the owner at an `owner-review` step. It never says in a prompt how a step is done and never does work in code.
- **Role** — `.claude/agents/<role>.md`: responsibility, inputs, steps, structured output, what it writes, and an Evaluation section with the signals `project-memory` judges it by. A role file holds the process only; what the role learns doing it lives in its memory (below). How a step is done lives only there, so a fix to a role is never overridden.

A loop's `kind` is `task` (the project's work, chosen by the owner and recorded with its parameter values in `.contrejour/loop.json`), `setup` (the framework's, which sets up the project's workflow) or `on-request`.

## Setting a project up

Every project's workflow is set up by the framework's `setup` loop, the same for all of them: the owner says what the project's work should be; `loop-query` finds the task loops that fit, `project-setup` proposes one with its parameter values, and `loop-authoring` changes or builds one when the owner asks; the project's loops are checked, and the hand-off records that the project is set up (`.contrejour/setup.json`). Setup reads `task.md` when there is one and never writes it: what a project works on is the project's, and so is any configuration it needs, which a package gives its projects as loops of their own. The Studio opens a project on its task loop, whether setup chose it or the example the project started from did (the example's task loop and values are recorded when the project starts, though no setup has run). A project without a task loop opens with this loop, except one started empty, which opens blank: the owner builds it in the chat and runs setup when they pick it from the loop list, where the framework's base loops and roles the project still has as installed are shown apart from its own; the owner of a project started from an example picks it there too, to set its workflow up differently. The entry role runs setup when the owner starts a project that is not set up.

## Base components

Some roles give a task loop a capability when one of its steps calls them. `project-memory` is memory and optimization at once: each role has its own memory, an LLM wiki in `memory/<role>/` written only through `memory.js` (`insert`, `update`; every write an event chained by its hash, the pages made again from the events, keys and tokens refused); a role whose frontmatter says `memory: on` first queries it for the kind of task it was given (`memory.js query`), then works, then ends; and the loop's last step (`optimize`) judges the run's roles by their Evaluation and inserts or updates in their memory what worked and what did not. Knowledge goes there, never into a role file: a new role holds only a brief process, and what its description knows is drafted as its first entries. `experiment-queue`, a loop, runs a stage's experiments as the owner's settings say (how many at once, how long each may run, when to stop the rest): each experiment is a command run detached under `experiments.js`, which records how it ends; the queue dispatches them, `watchdog` follows them, and the ones that stall, fail or run past their limit are stopped. `watchdog`, a role, follows long work on an interval: it waits in `watch.js` without the model until the work changes or the interval is over, then judges each task and says which to stop; a loop calls it again, within a bound, until nothing runs (the clock is a helper's, never a script's). A loop with an experiment stage is always asked whether that stage runs through `experiment-queue`; a loop that runs as another's child, which cannot run a loop of its own, is offered `watchdog` instead. Each says so in its frontmatter (`component`: what a task loop gains by it, and where its step goes), and `loop-check.js components` lists the ones a project has, its own included; a role or a loop becomes one by declaring it. When `loop-authoring` drafts a new task loop, `loop-query` finds them first and recommends which of the draft's loops (the task loop and the loops it runs as steps) add which, and which of its roles turn their memory on (`memory@<role>`); the owner confirms at an `owner-review`, `loop-editor` adds what the owner confirmed before the roles are drafted, and the owner approves the whole draft as for any loop. A change to an existing loop is offered none.

## Trying a loop

`loop-check` runs a script with stand-in roles: every step reachable, every role there, every send-back handled (below). `loop-trial` checks a loop the way it will run: after the static check it runs the loop for real on a small scale, with the `trial-args` its definition declares (a loop whose real runs would act outside the project declares none, or declares arguments that stop it short of that), `loop-tester` reports what the run did against the owner's goal, and the owner judges it. When it does not serve the goal, `loop-authoring` changes the loop's steps and `project-memory` writes what its roles should do differently into their memory, from the trial's trajectories, and the loop is tried again. A loop that runs a loop it is given names the argument that gives it (`child-loop-arg`), so the check can follow it.

## Sending back

The static check runs a script before it runs for real; sending back is the check while it runs. Every step checks what it receives against its role's Inputs: one that cannot use an input sends it back (`send_back`, in every role's Output) to the step that made it, which runs again with `returned` (in every role's Inputs: the step that sent it back and the problems), and then the step runs again on what it makes. A child loop is a step too: it may send back what it was given, which is made again before it runs again, and a loop whose result a step sends back runs again with `returned` in its arguments. Each step sends back at most 2 times in a row; past that, or when what it cannot use is the loop's own input (`caller`), the loop ends with `sent_back`, which its caller handles the same way. A redo that would change what the owner approved goes back through the owner's review. Every loop has it: the definition's Send back section says which step may send back to which; the check requires `send_back` in every step's schema but `owner-review`'s (the owner's `revise` is theirs), sends each step's input back to each step it may go to, one at a time, and reports a send-back the loop does nothing about; the role check requires `returned` and `send_back` in every role but `owner-review` and the roles sessions enter as.

## Waiting for the owner

Workflow agents cannot ask a person. A loop that needs the owner stops at `owner-review`, which writes a review note, and returns `{waiting: "owner", review_id, question, document}`. The session (or the Studio, through its session) shows the note and passes the owner's next message, verbatim, as `answers.<review_id>` when it runs the loop again, resuming the run. The `guard-owner-answers` hook checks each answer is, whole and word for word, a message the owner typed in that session after the loop stopped at that review (Claude Code 2.1.316 records typed messages without an origin, 2.1.317 with `origin.kind: "human"`), and blocks the run otherwise; `owner-review` accepts only the answers the hook recorded.

## Project packages

The framework knows nothing about any one project. A package tells it what it needs in `project.json`:

```json
{
  "format": 1,
  "name": "my-package",
  "profiles": {
    "default": { "entry_role": "task-manager", "sides": [], "next": ["what to do after installing"] }
  },
  "extension": "my-extension.js",
  "hook_actions": { "my-action": ["PreToolUse"] }
}
```

- A **profile** is a kind of machine a project can be installed as. `sides` name the library folders (`library/loops/<side>`, `library/roles/<side>`) its loops and roles come from, besides `framework`. A side's loop or role of the same name as the framework's takes its place.
- The **extension** is a module installed with the helpers that exports `extension` (`ProjectExtension` in `src/tools/project-manifest.ts`): the project's hook actions, the task a session works on (recorded with each trajectory), what counts as a finished task (one is needed before anything leaves; by default a run of the task loop), secrets and hidden files that must never leave, and whether what leaves needs a check of the project's own first (the `publish-check` loop, which records its verdict with `publish-cli.js record-check`, bound to the plan's digest).
- A side's **loops of the framework's names** take the framework's place in its projects. One is made for that: `publish-check`, the project's own check of what leaves (the framework's puts the files to the owner).
- `skills/shared-references/project-rules.md` holds the project's rules the framework's roles read: how its task loops are run, how its runs are identified and where their outcomes are, whether its trajectories hold what no role may contain (then `project-memory` only proposes what it would write, and the owner accepts in `proposal-review`).

Dependencies point one way: a project package depends on a version of this framework, as a git submodule, and the framework depends on no project. The community library holds published projects, each carrying every loop and role it needs besides the framework's, and checks each one by starting a project from it with this framework (below).

## Editing and publishing

There are two states. **Editing** happens in the Studio: an application installed once per machine, from a checkout of this repository, which keeps a workspace of projects (`~/agent-loop-projects` unless told otherwise; the owner switches to another folder on its Projects page, and the Studio remembers the choice in `.studio-settings.json` in its checkout, which git ignores). It starts projects (empty, from one of the framework's examples in `references/`, or from a project published to the community), copies, opens and deletes them (a deletion needs the project's name typed, and waits until no loop the Studio started works in it); it creates each project's folder with what Claude Code needs to run it (`.claude/`, the hooks, the runtime in `.contrejour/`) through the installer, which nobody runs by hand. The runtime holds the helpers the project's roles and hooks run, not the Studio, which runs only from the checkout, where its Claude Agent SDK is installed. Every machine that runs a project runs a Studio. **Publishing** puts a project in the community library, agent-loop-community, under `projects/<name>/`, as an example any project can start from (below).

`studio.js` serves the page (built by Vite from `studio/` into `dist/studio/`) and its data on this machine's own address only, to the one browser signed in with the link it prints; requests that act need the page's own header, so another site cannot act for the owner. It reads loops, roles and the trajectory index; it changes a project only through the owner's actions (creating, copying, opening or deleting a project, choosing the task loop and its values, fetching the community library beside its checkout, switching workspaces) and through loops run in sessions as the entry role (Run, Trial, Publish), whose progress it follows in Claude Code's run journal. It starts those sessions itself, through the Claude Agent SDK (`agent-sessions.ts`), which brings a Claude Code of the same version for the platform. A session is a child of the Studio's process with its input kept open: the owner's messages go in as they come, marked `origin.kind: "human"`, and a loop it runs in the background wakes it when the loop ends. How a session stands is what it reports: working until nothing is left, loops in the background included, then idle until the next message. The Studio keeps nothing else about it beyond the conversation's record of its id: the session writes its transcript as Claude Code always does, and the hooks and the chat read that. Sessions end with the Studio; a message afterwards continues the same session from its transcript, under the same id, and a loop that was running has to be started again. Two things differ from a plain `claude` and are set on purpose: the SDK's default prompt would leave the role's instructions out, so a session asks for Claude Code's own (`systemPrompt` preset) and takes the role's on top, and nothing is left waiting for an approval (`permissionPrompts: "none"`). A session started this way needs no trust recorded for its folder, and the Studio writes nothing in Claude Code's global config. The page hears of changes on `/api/events`, each session's state and the words it is writing, a few times a second; what happened it reads from the timeline. The chat shows a session's conversation as it goes (`session-timeline.ts`, on the design of Paseo's agent timeline, https://github.com/getpaseo/paseo, Apache-2.0): the transcript, read as it grows, becomes rows of one kind each (the Studio's prompt, the owner's messages, the session's words, a thought, a tool call whose status follows its result, notices, a turn's end) with Claude Code's bookkeeping left out; a loop is a row of its own that runs until its notification, with its run's roles from the journal beside the transcript, each role's own transcript read when the owner opens it; a tool call's output or diff is read only when it is opened. The page groups runs of tool calls into one sentence, folds a finished turn under its last words, follows the end while the owner does, queues a message while the session works, and stops it on request (an interrupt, which stops the loop it runs too). A message goes to the conversation shown, waiting at a review, idle or no longer running, until the owner starts a new one. It reads a session's transcript where Claude Code keeps it (`$CLAUDE_CONFIG_DIR/projects`, or `~/.claude/projects`); when a turn fails, the chat shows why in Claude Code's words (an API error it could not get past, say), and says when the transcript is missing, since without it neither progress nor result can be followed. In the chat, the owner points at a step, an arrow or a parameter by clicking it on the canvas or by typing `@` and picking it from the list; either way the pointer goes to the loop with the owner's words. There is one chat box: a reply goes to the loop waiting for it; with a loop on the canvas (or a role chosen), the words go to `loop-authoring` (or `role-authoring`), whose own steps find the loops close to them or change the one shown; with nothing on the canvas yet, the close loops are found at once and the closest is shown. The roles, loops and steps the chat names light up on the canvas when clicked, the rest greyed.

## Libraries

A project's loops and roles come from the `library/` of the checkout it was installed from, and, for a project package's checkout, of the framework's it carries as a submodule (`agent-loop-studio/`). The framework's `framework` folder holds its own base loops and roles; a package's folders hold its own sides'. Examples come from the framework's `references/` and from the community library's `projects/`, cloned beside the checkout as `agent-loop-community/` (git ignores it there). An example's loops and roles take the place of a framework one of the same name in a project started from it. The installer keeps a copy of each loop and role it seeds as its baseline (`.contrejour/seeded/`): one the project has changed since, or got from its example (`.contrejour/reference.json`), is the project's own and is never replaced; one still as seeded (both halves, for a loop) is the library's as installed, and installing again brings it to the library's new version with its baseline. The Studio does that when it opens a project whose installation is behind its checkout (a dry run of the installer tells), and says in the chat what it brought up to date. A role's `effort` goes to the model's provider as written: it is `low`, `high`, `xhigh` or `max`, or left out to use the session's own, since some providers (DeepSeek among them) refuse `medium`; the role check enforces it.

## Optimizing and publishing

What a project improves stays in the project: `project-memory` writes what its roles' trajectories show into their memory, in the project (or proposes it, when the project's rules say so), and the owner changes its loops and roles in the Studio. Whether any of it leaves is the owner's decision, made by publishing: the `publish` loop puts the whole project under `projects/<name>/` in the community library, once one of its tasks has finished. It holds `reference.json` (a title and description in Chinese and English, which `project-publisher` writes, and the task loop with its values) and every loop and role that is the project's own: the ones it made, the ones it got from the example it started from (`.contrejour/reference.json` records them), and its versions of the framework's base ones. The framework's base loops and roles it left as installed stay out, and so do its data, keys, `task.md` and run records.

`publish-cli.js` keeps the record of what each publication sent, so a later one sends only what changed and removes what the project no longer has; a name another project publishes under is never overwritten. It blocks keys, tokens and hidden files, warns about paths of this machine, checks the publication over the framework's library as a project started from it gets it, runs the project's own check when it has one (`publish-check`), and the owner approves exactly what leaves before the one pull request is opened. `.contrejour/published.json` records the project's latest publication, which the Studio shows. The community library checks every project it holds the way a project starting from it gets it: its `tools/check.mjs` installs a new project with the framework's installer, gives it the published project with `applyExample` (`workspace.ts`, the code the Studio uses), and runs the loop and role checks on it.
